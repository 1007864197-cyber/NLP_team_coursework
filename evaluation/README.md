# Evaluation protocol

This directory contains a small, **synthetic, manually authored evaluation set**. It is not a sample of real restaurant customers and is not evidence of production performance.

The evaluation compares the application's `baseline` and `enhanced` response modes on the same fixed queries. Each single-turn item starts with a fresh conversation state. Separate scenario checks exercise conversation state across several turns.

## Data and split

- The restaurant FAQ is the system's reference knowledge, not an evaluation split.
- `queries.json` contains paraphrases authored for evaluation, including misspellings and out-of-domain messages. These are not verbatim copies of FAQ questions.
- Classifier training uses the separately authored groups in `training/data/intents.json`. Those groups are split within class into training and development data; polite-prefix augmentation is applied to training groups only. Candidate-model and threshold selection use development data. The FAQ is also reference knowledge for lexical retrieval. None of the query texts in this evaluation file are supplied for model fitting or threshold selection.
- The query set is a separate, fixed diagnostic test set, authored with knowledge of the supported categories. It is not an independent natural-user benchmark. If it is later used to tune rules or thresholds, it must be treated as a development set, and a new untouched test set is needed for an unbiased estimate.
- Labels express the intended FAQ category or rejection behavior. A matching label does not prove that every sentence of an answer is factually correct.

## Measures

`run_evaluation.py` reports the actually observed intent accuracy, macro F1, retrieval acceptance and rejection measures, per-category support and scores, and per-request latency (median and 95th percentile). Its main comparison runs the full dialogue system in `baseline` and `enhanced` modes, including any enabled classifier and dialogue routing. A separate raw-retrieval comparison calls `retrieve()` directly and must not be confused with the full system. The result records those groups separately.

Rejected responses use the out-of-domain label for intent scoring. A full-system accepted retrieval means a non-fallback answer with at least one returned reference source. Correct accepted retrieval additionally requires a matching category. Raw retrieval instead uses a non-fallback category and a non-empty `source_id`. These are category-level, source-presence measures, not claims of calibrated confidence, entailment, or hallucination detection. The single-turn corpus covers the 14 FAQ categories and rejection; it does not estimate classifier performance on every training class. Dialogue/recommendation behavior is checked separately by scenario tests.

Latency is measured in the local Python process after a warm-up call. It excludes server, browser and network startup, and depends on the machine and other workloads. The 95th percentile is a sample percentile; this small sample does not establish a reliable production tail-latency bound.

Run from the project root:

```text
python evaluation/run_evaluation.py
python -m unittest discover -s tests -v
python tests/smoke_interfaces.py
```

The evaluation writes `results/results.json`, `results/results.md`, and `results/predictions.csv`. These files are generated by executing the system; no result numbers are entered manually. The output records the UTC run time, Python version, corpus digest, measured call count, and mode definitions so a run can be identified.

The unit tests check user-visible contracts and input handling. They do not enforce a particular evaluation score or claim that the authored sample represents real users.

The optional smoke script starts a real localhost HTTP server on an ephemeral port, checks the page/health/chat endpoints, shuts it down, and runs a short piped CLI conversation. It prints whether the trained model was loaded; a retrieval-only smoke pass is not proof that model integration succeeded.
